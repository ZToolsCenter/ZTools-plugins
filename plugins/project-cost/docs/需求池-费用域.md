## 0. 三条不可突破的约束（所有需求都按这三条筛过一遍）

| 约束 | 对需求的直接含义 |
| --- | --- |
| 窗口固定 800×618，左轨 62px，内容区 738px，抽屉 392px | 任何需求都不能靠"再加一列 / 再加一个页签"实现；新增信息必须复用已有行内空间或进抽屉 |
| 数据只在本机 localStorage（约 5MB），无后端、无账号 | 不做多端同步、不做定时任务、不存图片；所有"历史版本"类需求必须自带体积上限 |
| 单人或家庭协作记账（付款方视角） | 不做权限、审批流、审计日志；"谁改的"没有意义，"什么时候改的、改了多少"才有意义 |

另有一条产品底线：**金额链唯一真源不变** —— 明细合计 → 费用项总计 → 应付（−优惠）→ 已付（Σ付款）→ 待付。下文任何需求都不得引入第二个金额真源（这是 B1、C3、A1 等需求的设计前提）。

## 1. 优先级与成本口径

**优先级**

| 级别 | 判定标准 | 含义 |
| --- | --- | --- |
| P0 | 不做会导致**记账出错**或**数据丢失** | 属于"修地基"，做完才能安心加功能 |
| P1 | **显著减少重复劳动**，或让报表**可用于决策** | 决定用户是否愿意长期记下去 |
| P2 | 锦上添花 | 有余力再做，可被延后不影响使用 |
| P3 | 非核心边缘场景的体验/安全网补强（如首会话备份、无障碍偏好持久化）；不做不影响记账正确性 | 评审最低档，排在 P2 之后 |

**成本**（按单人开发、沿用现有技术栈估算）

| 标记 | 工作量 | 典型形态 |
| --- | --- | --- |
| S | ≤ 0.5 天 | 单文件改动、加字段、加一行提示 |
| M | 1–2 天 | 新增抽屉或分析页签、纯函数 + 视图联动 |
| L | ≥ 3 天 | 涉及数据迁移、解析器、或跨模块改造（本文无 L 级需求，刻意控制） |

## 3. P0 推荐三条

选这三条的唯一标准：**它们坏掉的时候用户不会收到任何报错，只会默默算错账，或者默默丢数据。**

### ① Q1 自动快照与一键回滚 —— 先保住数据，再谈功能

现状最危险的一点不是"缺功能"，而是**全部身家只在一个键里，且没有任何自动保险**：清缓存、升级插件、配额溢出、误点「导入 JSON」（`importState` 现在是整包替换 `state.books`，连撤销快照都没存）—— 任何一个动作都能让 384 条明细消失，而现有撤销只活 5 秒。

做完之后用户少做的动作：**不用再记得每周手动导出 JSON 备份**（这是最容易被高估的自律，也是最容易失效的保险），出事时点一次「回滚」即可，不再需要重录。

顺带把「导入 / 清空 / 恢复默认」三个破坏性操作统一挂到快照上 —— 这是同一套机制，几乎零额外成本。

### ② C1 付款流水补全 —— 让"已付"这个数字可追溯

现在 88 笔付款只有日期、方式、金额，且历史数据里有一批**没有日期**。后果是链式的：没有备注 → 分不清定金还是补差 → 月底对账靠猜 → 重复付款或漏付；没有日期 → 月度趋势与逾期判断失真；没有凭证号 → 找不到对应转账截图。付款是这个产品的第二个数字来源（已付 188,529.11 全靠它），它比费用项更该有据可查。

做完之后用户少做的动作：**不再需要打开微信账单/银行 App 逐笔反查**每笔付款是什么用途，对账从"回忆"变成"检索"。成本只有 S（两个字段 + 两个输入框 + 导出两列），是本文性价比最高的一条。

### ③ Q2 数据体检与一键修复 —— 让口径不一致自己浮出来

`calc()` 里的「预算合计」与 `catRows()` 的 14 行预算加总，在某些操作后会对不上（改过品类名、导过旧数据、删过档案）。用户看到的是两个互相矛盾的数，既不知道为什么，也不知道从哪查 —— 于是开始不信任何数字，台账就废了。

做完之后用户少做的动作：**不用再一行行手工核对"预算合计为什么和品类加总不一样"**，也不用在高雄心疑时重录一遍台账；报出问题时能看到"这条差 1,860，原因是 2 条费用项引用了已删除的品类"，并且一键修好。

**顺序建议**：Q1（保命）→ C1（记账正确性，成本最低）→ Q2（口径自检）。三条合计约 3 天，可与 v1.2 一起发一版，先跑满验收再谈 P1 级的批量需求。

## 4. 不建议做（6 条，附理由）

| 不做 | 理由 |
| --- | --- |
| 票据/发票图片附件（base64 存本地） | 与 5MB 配额直接冲突：一张手机照片压缩后仍 200–400KB，存十几张就撑爆；`persistNow` 现在就已经在"配额满时静默删图"，说明这条路走不通。800px 抽屉里看图也看不清。**替代**：C1 的凭证号/备注文本字段，够用来找图 |
| 供应商比价（同品名跨收款方价格对比） | 单项目里同一品名通常只有 2–3 条记录，样本量不足以支撑比价结论，算出来的是噪声；要做准就得强制品名口径统一，维护成本远高于收益 |
| 自定义字段 | 需要动态表单 + 动态列表 + 动态导出表头三处联动；738px 内容区每加一个字段就挤掉一个现有信息位（品类/收款方/日期/明细数）。现有 9 个字段已覆盖个人记账场景 |
| 周期性支出自动生成（房租/物业/水电） | 插件不常驻、无后台定时器，只能在打开时补生成 —— 等于每次启动都问"要不要补记 3 笔"，比现在「复制费用项」（R4）更烦，且容易生成重复账 |
| 桌面通知 / 系统级提醒 | ZTools 当前 preload 只暴露 `setExpendHeight / showToast / onPluginEnter / onThemeChange`，没有通知 API；插件不常驻更无法主动推送。**替代**：左轨角标 + 概览横幅（已有），做 M1/M2 增强即可 |
| 收支双向（收入 / 客户回款） | 当前用户是**付款方**视角（费用台账 + 收款方档案），加收入等于把产品改成"项目损益表"，需要客户、合同、开票三块支撑，是另一个产品。退款已由负数付款覆盖，够用 |

## 5. 边界待定项（需用户确认是否纳入费用域）

> 以下功能**强依赖合同或进度**才能成立。若只做费用域，它们会退化成"多一个日期列表"或"多一个标签"，收益不足以抵消概念膨胀；若确认纳入，则应跟《PRD-项目管理升级》的合同/阶段一起排期，而不是单独塞进费用域。

| 编号 | 边界功能 | 依赖 | 只做费用域会退化成什么 | 需用户确认 |
| --- | --- | --- | --- | --- |
| N1 | 承诺成本 vs 实际成本（契约额口径） | 合同金额 + 变更单 | 没有合同，"承诺"只能等于应付，两个口径是同一个数 | 是否纳入费用域 |
| N2 | 分期付款计划 / 付款节点（预付 30% / 进度 40% / 尾款 25%） | 合同节点或阶段 | 退化成"一个费用项挂多个到期日"，与现有到期日字段语义冲突 | 是否纳入费用域 |
| N3 | 质保金 / 尾款台账（竣工后 N 个月释放） | 合同 + 竣工日（进度） | 退化成普通费用项 + 一个未来到期日，无法自动释放提醒 | 是否纳入费用域 |
| N4 | 变更单对预算基准的影响（保护原预算 / 抬高基准） | 合同变更记录 | 退化成"改预算 + 记一条备注"，无法区分是追加还是失控 | 是否纳入费用域 |
| N5 | 按阶段归集费用（阶段成本核算、阶段超支预警） | 进度阶段 | 退化成给费用项加一个"阶段"标签（最小版本可实现，但需先确定阶段来源） | 是否纳入费用域，或只做标签版 |
| N6 | 按完成进度确认应付（已完工程度 → 应付金额） | 进度 % | 退化成手工分次改金额，破坏"明细为唯一真源" | 是否纳入费用域 |

## 6. 与其他文档的关系

- 本文只做**费用域**的需求收敛，不替代《PRD-项目管理升级.md》。后者是"从费用管理走向项目管理"的整体方案（阶段/合同/交付/问题），其中 F14 附件与留痕、F18 完工报告与本文第 4 节、X4 有重叠 —— 本轮的判断是：**附件不做（配额不允许），完工报告的"费用部分"用 X4 项目结算单先行满足**。
- 若用户确认要做阶段/合同（第 5 节任一项），建议顺序是：先落 Q1/Q2/C1（数据与口径地基）→ 再做阶段 → 再做合同节点。地基不稳时叠合同，返工成本最高。

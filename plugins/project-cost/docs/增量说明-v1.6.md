# 增量说明 v1.6.0（K1 / C5 / C4）

> 批次定位：v1.3 的 X1（CSV 三表回读）留了一个**会算错账**的口子 —— 付款行只能靠
> 「项目号 + 日期 + 金额」猜行，**同一项目同一天有多笔付款时，导回单行永远命中第 1 笔**。
> 本批先把这条地基补上（K1 付款唯一键），顺带把付款流水「可追溯」的最后两块补完：
> 记错了能留痕作废（C5）、月底一次给多笔（C4）。
>
> 三条都在**付款域**，共用一套口径：`paidOf` 是全站唯一的「已付」真源。

## 0. 一句话结论

- 新增 3 个能力，**金额链真源三项字面不变**：应付 246,055.97 / 已付 188,529.11 / 待付 57,526.86；
  B1 派生 231,180.97 / 14,875.00 不变，预算 234,688.00 / 结余 −11,367.97 不变。
- 数据结构：付款记录多两个字段 `pid`（项目内唯一编号，如 `P0001`）、`void`（作废标记）。
  老数据打开自动补齐，**不迁移、不重排、不丢号**。
- 导出契约：付款表在末尾追加 `付款编号`、`作废` 两列（前 8 列逐字不变）。
- 测试 **901 例全绿**（v1.2 回归 146 + v1.3 358 + v1.4 99 + v1.5 181 + v1.6 117）。

## 1. K1 付款唯一键（修的是「会算错账」的缺陷）

**问题现场**：某费用项 3 月 1 日付了两笔（1,000 与 2,000）。导出付款表 → 把第二笔改成 2,500 →
「按编号覆盖」导回。旧规则按「同项目 + 同日期的第 k 次出现」定位，单行 CSV 的 k 恒为 0，
于是**改的是第 1 笔**：第 1 笔变成 2,500、第 2 笔还是 2,000，已付虚增 1,500。全程没有任何报错。

**实现**
- `core.js`：`PID_RE = /^P\d{4,}$/`、`nextPid(payments)`（取项目内 max + 1）、
  `ensurePayIds(payments)`（就地为缺失/非法/重复的付款补号，**幂等**）。
  规则集中在 `ensurePayIds` 一处 —— 加载回填与测试夹具共用同一份，不出现第二套编号逻辑。
- `store.js`：`normalizeBook` 调 `ensurePayIds`；`upsertPayment` 新增时发号、编辑时**沿用原号**
  （编号是身份不是序号）；`importTable('pay')` 三策略**一律先按 pid 定位**，无 pid 才退回旧规则。
- `export.js`：`HEADS.pay` 末尾追加 `付款编号` / `作废`；`payRows` 输出两列。
- `parse.js`：`TABLE_COLS.pay` / `FIELDS.pay` 同步；`mapRow` 校验 `付款编号` 格式，非法一律视为未填
  （不因一个可选列把整行判死）。
- 顺带修掉一个**每次导出→导回都丢 6 笔**的老问题：历史台账里的无日期付款原本被判「缺少付款日期」
  进坏行。现在有编号的行允许日期留空（编号本身就是定位依据），导出→导回 finally 无损。

**验收**：单行改 2,500 导回后「覆盖 1 / 新增 0」、第 1 笔仍是 1,000、已付增量正好 500；
原样导回 88 行「覆盖 88 / 新增 0」且 pid 集合逐字不变。

## 2. C5 付款作废留痕（作废 ≠ 删除）

**问题**：记错的付款点删除就没了痕迹。真对银行流水时回答不了「那笔 5,000 是记错了还是真没付」——
而这个答案恰恰只能从「留着的错误记录」里得到。

**实现**
- `core.js`：`activePayments(p)` / `voidPayments(p)`，`paidOf` 改为**只累加未作废付款**。
  这是全站唯一一处过滤 `void` 的地方；`monthCompare` 的已付、`monthlyPayments`、
  `checkup` 的「付款缺少日期」全部改走 `activePayments`（作废款不参与环比、趋势、体检）。
- `stats.voidCount`：作废笔数单独计数，**不混进 `payCount`**（否则「88 笔流水」与已付金额对不上）。
- `store.voidPayment(projectId, index, flag)`：切换作废态，幂等；一次 `pushUndo`。
- `upsertPayment`：编辑一笔已作废的付款**保持作废态** —— 要恢复必须显式点「恢复」，
  避免改个备注就把一笔已对账的款悄悄复活。
- `dupPaymentExists` 跳过作废记录：「记错了 → 作废 → 重新记一笔」是最常见的正确流程，
  若把作废记录也算重复，用户会被自己的历史挡住。
- UI（`ItemSheet`）：付款行新增「作废 / 恢复」按钮 + 作废后整行灰显 + `作废` 小标签 + 删除线；
  `.mrow.payrow` 单独加一列（不动 `.mrow`，明细行仍是 3 列，避免列宽串位）；
  彻底删除的确认文案改为「不保留痕迹，已付立即减少，若只是记错请用作废」。
- 对账单（C3）只列有效流水 —— 给收款方看的单子上不该出现内部作废款。

**验收**：作废后已付减少 / 待付增加该笔金额、pid 与凭证号不变、记录仍在；恢复后逐分回到原值；
导出带 `作废=是` 的文件导回后**仍是作废**（不会被复活），已付不变。

## 3. C4 批量登记付款

**问题**：月底一次性给同一个工长转 5 笔，要开 5 次抽屉、填 5 次日期与方式。

**实现**
- `store.planBatchPay(ids, total, mode)`：**纯计算不落库**。`due` 按待付比例分摊、`even` 均分，
  **最后一行吸收分角差额**，因此 Σ分配恒等于总额（不会出现「三笔加起来 9,999.99」）。
  允许总额超出待付合计（超付是合法事实），此时按同比例放大并回传 `over`，**不静默截断**。
- `store.batchPay(...)`：按 `planBatchPay` 的结果一次落库，整批一次 `pushUndo`（撤销一步到位）。
- 前端**预览与落库共用同一个函数** —— 预览说 3,333.33、实际写 3,333.34 这类漂移结构上不可能发生。
- UI（`ItemsView` 批量操作条）：「批量付款」→ 面板内「总额（预填所选待付合计） / 分配方式 / 日期」
  + 每笔分配预览 chips + 「登记 N 笔」。

**验收**：勾 3 条待付、总额 10,000 → 流水 +3、三条待付合计精确减少 10,000、每笔都有唯一 pid；
100 元分给 3 条待付各 100 的费用项 → 33.33 / 33.33 / 33.34，Σ 精确 100。

## 4. 改了哪些既有契约（升级须知）

| 契约 | 变更 | 影响 |
| --- | --- | --- |
| 付款表表头 | 8 列 → 10 列，末尾追加 `付款编号` / `作废` | 旧的 8 列文件仍可导入（无 pid 走旧规则） |
| 付款记录字段 | `{date, method, amount, note, ref}` → 追加 `pid` / `void` | 打开老账本自动补齐 |
| 「已付」口径 | Σ全部付款 → Σ未作废付款 | 无作废记录时数值完全不变 |
| 无日期付款的导入 | 原先一律判坏行 → 有 `付款编号` 时允许留空 | 导出→导回不再丢 6 笔 |

## 1. 版本目标与一句话价值

**一句话：让屏幕上每个数字都敢拿去对账。**

v1.7 不加功能，修的是**可信度**——三件事：

| 目标 | 具体含义 | 本批承载 |
| --- | --- | --- |
| 数字不再自相矛盾 | 屏幕与 Excel 同口径、正负号不丢、精度不混用 | A1 · C2 |
| 口径只有一个来源 | 品类数、未设预算、超支分类、搜索、编号各只有一套判定 | A2 · B1 · C6 |
| 出错能退、数据能走 | 连撤 20 步、一键备份出本机 | A3 · B4 |

不做功能扩张：13 项里 **P0 2 条（A1/A2）** 是「会算错、看不出来」，其余是按决策效率与信息密度排序的修补。任何一条都不得引入第二个金额真源（见 §7 红线自检）。

## 2. 口径决策表

> 原则：每项**只给一个口径**，不留「待定」。表内数字均为基线实测值。

### 2.1 A1 负数显示

| 决策点 | 唯一口径 |
| --- | --- |
| 显示形态 | 正数 `¥394.88`；负数 `-¥394.88`（负号在货币符**前**，禁止 `¥-394.88`）；零 `¥0.00` |
| 零的判定顺序 | 一律 `round2(n)` → 再判 `v < 0`（`-0 < 0 === false`），因此 `-0.001` 显示 `¥0.00`，**永不出现 `-¥0.00`** |
| 无货币符的列 | 列表行内金额、抽屉 `.amt`、表内数字列：`-394.88`（不带 ¥，带负号） |
| 颜色 | 明细行 / 合计 / 总计 / 待付的负数 → `--danger`；**付款行负数例外**：保留「退款 394.88」文案 + `--ok`（资金回流不是超支，删掉这三个字反而看不懂） |
| 函数收敛 | 全站只留 3 个出口，全部在 `core.js`：`fmt(n)`＝带 ¥ 带符号；`fmtNum(n)`＝**语义改为带符号**（原 `Math.abs` 去掉）；新增 `fmtAbs(n)`＝绝对值 |
| 为什么要改 `fmtNum` 语义而不是新增函数 | 全站约 48 处 `fmtNum` 调用点，绝大多数本来就该带符号（明细、合计、待付、欠款），改语义可一次性修好；只有下表 8 组「用文字或符号已经表达了方向」的位置必须显式改用 `fmtAbs`，否则会出现 `＋-`、`余 -1,234`、`超 -800` 这类双信号 |
| 8 组必须改用 `fmtAbs` 的位置（逐一复核，不得遗漏） | ① `OverviewView` 品类「超 / 余」文案 ② `BudgetView` 顶部「结余 / 超支」 ③ `BudgetView` 收款方「欠 / 多付」 ④ `PayeeForm` 「多付」 ⑤ `CatForm` 未设预算差额 ⑥ `AnalysisView` 环比（已有 ↑↓ 箭头） ⑦ `PayView` 「含超付」 ⑧ `StatementSheet` / `ItemSheet` 的「退款」「超付」两处文案 |
| 反向自查 | 改完后全站文本不得出现 `--`、`+-`、`¥-`、`余 -`、`超 -` 五种形态（写成断言扫描 6 个视图的渲染文本） |
| 导出 | 数值列**继续写原始有符号数**（`export.js` 不改数值逻辑）；本次要修的是屏幕侧。改完后 Excel 的 `−394.88` 与屏幕的 `-394.88` 首次一致 |
| 对账单 / 打印 | 与屏幕同口径（走同一个 `fmtNum`） |

### 2.2 A2 未设预算

| 决策点 | 唯一口径 |
| --- | --- |
| 判定 | `hasBudget(name) = Object.hasOwn(book.budget, name) && +book.budget[name] > 0`。**缺键**与**值=0/空**同属「未设预算」，只有一套语义 |
| 数据层 | **不补键、不写 0**（不因「显示」而改数据）。`book.budget` 仍是 13 个键，`sumBudget`/`totalBudget` 一分不动 |
| 为什么 | 写入 0 会让「未设预算」与「预算是 0」在数据层重新混成一种状态——正是 A2 要消灭的裂缝 |
| 预算页行 | 未设预算行：预算输入框留空 + placeholder「未设预算」，占用率列显示 `未设预算`（不显示 `0%`），差额列显示 `—` |
| 超支两类命名 | 「**超预算**」＝有预算且 `confirmed > budget`（B1 确定应付口径）；「**未设预算**」＝无预算且 `confirmed > 0` |
| 排序与行数 | 超预算：按超出额降序；未设预算：按确定应付降序。两组**分组展示、不混排**，组头给「总数 + 合计」，每组最多渲染 5 行，超出显示 `还有 N 个`（基线：超预算组 6 个 → 5 行 + `还有 1 个`；未设预算组 1 个 → 1 行）。不出现把两类合并的「超支 N 个」 |
| 基线值（验收锚点） | 超预算 **6 个品类**，超出合计 **+12,266.75**（泥瓦镶贴 +768.00 / 细部收口 +2,688.00 / 楼梯栏杆 +1,800.00 / 卫浴洁具 +2,537.00 / 厨房设备 +2,486.25 / 墙顶涂饰 +1,987.50）；未设预算 **1 个品类**：其他费用 **9,514.00**（3 项） |
| 三处品类数文案模板 | 统一函数 `catCoverage(book)` → `{total:14, withBudget:13, missing:1}`，文案只由它生成：**`14 个品类 · 13 个已设预算`**。落点：① 概览「项目总预算」卡片小字（原 `13 个品类`）② 预算页汇总行（原 `13 个品类已填预算`）③ 预算页页签（原 `品类预算 14`，保留 14）④ 分析页「预算 vs 实际」标题右侧（新增 `共 14 个品类 · 13 个已设预算`） |

### 2.3 A3 撤销栈

| 决策点 | 唯一口径 |
| --- | --- |
| 深度 | **20 步**（环形栈，超出淘汰最旧） |
| 体积上限 | 栈总字符数 ≤ 2,000,000（实测单账套快照 54,188 字符 ≈53KB；20 步 ≈1.03MB 内存，安全）。超限先丢最旧 |
| 是否持久化 | **否**。内存态，刷新/重启即清空。理由：写进 localStorage 等于把 5MB 配额切成 20 份，与 Q1 日快照抢空间；撤销是「刚才手滑」的补救，不是历史版本（历史版本已有快照机制） |
| 什么算一步 | 一次用户动作 = 一步。批量操作（批量改品类/收款方/到期日/删除/批量付款 N 笔）**整批算 1 步**，与 v1.6 `batchPay` 的「整批一次 pushUndo」一致 |
| 入口 | ① `Ctrl/Cmd+Z`（现有 `onKey` 在 `metaKey/ctrlKey` 时直接 return，需在 return 之前插入分支）② toast 里的「撤销」按钮（保留，行为不变）③ 设置页「快捷键」表新增一行 |
| 提示文案 | 撤销成功：`已撤销（还可退 N 步）`；N=0 时：`已撤销（已到最早）`；栈空再按：`没有可撤销的操作` |
| 与快照的关系 | 回滚快照（`restoreSnapshot`）后**清空撤销栈**（与现 `clearUndo()` 一致），避免撤到「回滚之前」这种跨版本状态 |

### 2.8 C1 术语

**术语三层（必须先分清，否则「项目」一词指两样东西）**：

| 层 | 数据实体 | 界面统一叫法 | 说明 |
| --- | --- | --- | --- |
| 账本 | `book` | **项目** | 顶部切换器里的「自宅装修 / 门店改造」 |
| 一笔支出 | `project` | **费用项** | 列表一行 |
| 一笔资金动作 | `payment` | **付款** | 抽屉里的付款流水 |
| 交易对手 | `payee` / `object` | **收款方** | 档案与筛选 |

**逐词替换清单**（旧 → 新）：

| 旧词 | 出现位置 | 新词 | 是否改导出 |
| --- | --- | --- | --- |
| 支出 | 左轨导航 `items` label、概览 KPI 小字「N 条支出」、「最近支出」、列表空态与删除确认、预算页「N 条支出」、设置页 KPI「支出」、新建按钮「新增支出」、toast「已删除 N 条支出」 | 费用项 | **表头与文件名不改**（仍是「支出表」） |
| 支付对象 | 费用项表单 label、预算页页签「支付对象 N」、付款页「所有支付对象均已结清」、设置页「品类 / 支付对象」、收款方抽屉标题「编辑/新增支付对象」、删除 toast、批量改「改收款方」提示 | 收款方 | **导出列名不改**（仍是「支付对象」） |
| 费用备注 / 事项 | 表单 label「费用备注」 | 保留「费用备注」 | 不改（列名一致） |
| 支付 / 已支付 / 待支付 | 概览与设置页 KV | 已付 / 待付 | 不改表头（表头本就是「已付 / 待付」） |

**导出与导入的兼容策略**：

| 项 | 决策 |
| --- | --- |
| 导出表头 | **一个字都不改**（含「支出表/明细表/付款表」文件名）。老文件与新文件必须能互相导入 |
| 导入列名 | 双名兼容：`COL_ALIAS = { 收款方 → 支付对象, 事项 → 费用备注 }`。只收「界面新词」到「表头旧词」的映射，方向固定单向（旧词本来就能命中，不需要反向别名） |
| 归一位置 | 在 `parse.alignByHeader` 与 `isHeaderRow` **之前**统一归一（同一个函数 `normalizeHeader(cell)`）。只改 `alignByHeader` 不改 `isHeaderRow` 会导致「表头只写收款方」时命中数 < 2 被判成数据行 → 整表错位 |
| 界面 | 表单 label、页签、空态、toast 全改 |

| 判定规则 | 收款方名 `trim()` 后满足任一：① 以 `-` `－` `—` `_` 结尾；② 以之开头；③ 长度 ≤1；④ 含连续分隔符（`--`）。命名建议归一时**只报不改** |
| 体检项 | `code: 'payee-name-suspect'`，`level: 'warn'`，`fix: null`，`fixLabel: ''`，`unit: '条'` |
| 展示 | 标题「收款方名疑似不完整」；`count`/`amount` 给条数与金额影响；`samples` 前 3 条（`泥工- · ¥14,980.00`） |
| 只报不改 | 不提供一键修复按钮；不自动改名、不改 `payees` 档案、不改 `p.object` |
| 基线锚点 | **2 条 / 26,780.00**：ZX0020 `泥工-` 瓷砖人工费 14,980.00、ZX0061 `木工-` 木工工资 11,800.00 |
| 与 `orphan-payee` 的关系 | 两条**独立**，可同时命中（`泥工-` 档案存在 → 只命中本条） |

### 2.12 C5 内部编号与联动提示

| 决策点 | 唯一口径 |
| --- | --- |
| 「内部编号」定义 | 仅指付款流水号 `pid`（`P0001`）。**项目号 `ZX0024` 是对外编号，列表照常显示** |
| 默认态 | 抽屉详情态付款行**不渲染** `pid`；列表页从不显示；付款编辑表单顶部显示 `编号 P0001`（编辑态可见） |
| 复制/对账场景 | 需要引用编号时由 C6 的全号承担（导出/合并视图），界面不靠常驻显示 |
| 联动提示 | 抽屉明细区底部提示**仅在不一致时出现**：`合计与总计不一致：相差 ¥12.00`；一致时**整块不渲染**（不占位、不留空行） |
| 为什么删掉「✓ 明细合计 = 项目总计（自动联动）」 | 明细区标题已写 `N 条 · 合计 X`，总计在金额卡里——一致是常态，常态不需要宣布 |
| 阈值 | 沿用 `|dSum − total| < 0.5` 判为一致（1 分钱容差），与 `checkup` 的 `TOTAL_DRIFT` 同口径 |

### 2.13 C6 编号前缀

| 决策点 | 唯一口径 |
| --- | --- |
| 费用项前缀 | `book.noPrefix`（string），默认 **`''`**＝沿用 `ZX` |
| 校验 | `^[A-Z]{1,4}$`；空允许；非法不保存并提示。只影响**新建**，旧编号一个字不动（与需求池 S1 一致） |
| 生成 | `nextNo(projects, prefix)`：取匹配 `^${prefix}\d+$` 的最大序号 +1，序号 4 位补零（`MZ0001`）。不匹配前缀的旧号不参与取号 |
| 付款全号 | `payNo(projectNo, pid) = \`${projectNo}-${pid}\``，例 `ZX0024-P0001`。**唯一函数**，导出/界面/未来合并视图共用 |
| 存储 | 内部**仍只存 `pid`**（`P0001`）与所属项目 id；绝不存全号（存了就会与项目号变更脱钩） |
| 跨项目合并视图 | 本批**不新增**合并页面（成本 L 且无数据支撑，目前账套切换是单账套视图）。只把 `payNo` 与导出格式定死，将来合并视图直接复用 |
| 导出格式 | 付款表「付款编号」列由 `P0001` → `ZX0024-P0001`；**导入必须剥离前缀**还原为 `P0001`，否则违反 v1.6 K1 唯一键（详见 §4） |

| --- | --- | --- | --- | --- |
| 支出表 `HEADS.proj`（14 列） | 无 | 无（数值列仍写原始有符号数） | 能 | 不需要 |
| 明细表 `HEADS.detail`（12 列） | 无 | 无（负金额本就以负数写入，A1 只修屏幕侧） | 能 | 不需要 |
| 付款表 `HEADS.pay`（10 列） | 无 | 「付款编号」值：`P0001` → `ZX0024-P0001` | 能（导入剥前缀，见下） | 不需要（双向兼容，不加开关） |
| JSON 备份 | 无结构变化 | 文件名变化（含条数） | 能（`importState` 同构） | 不需要 |
| 收款方对账单 CSV | 无 | 负数按带符号输出（`-394.88`） | 能 | 不需要 |

**付款编号「加前缀但不破 K1」的三条硬要求**：

1. `parse.mapRow('pay')` 在校验 `pid` 前先剥离前缀：新正则 `^(?:[A-Za-z]{1,8}\d{2,})?-(P\d{4,})$` → 取 group1；同时保留老的 `/^P\d{4,}$/` 直通。剥离后存回 `pid` 的**永远**是 `P0001` 形态。
2. `store.importTable('pay')` 三策略仍按 `pid` 定位，逻辑一行不改——因为传进去的已经是剥离后的 pid。
3. 「付款编号非法一律视为未填」的兜底**保留**：剥离失败 → 当未填 → 走旧规则补号（宁可回退到旧行为，也不能把前缀当编号写进库）。

**为什么不做「导出格式开关」**：开关意味着两套导出、两套导入、两套测试。双兼容（新写全号 / 老格式照读）在解析层是 3 行代码，成本远低于一个用户永远不知道该选哪个的开关。

**受影响的既有断言（预警给架构师 / QA）**：

- `verify-v16.mjs:111` `eq('payRows 第 9 列 = pid', payRows(B())[0][8], …pid)` → **会失效**，改为断言 `payNo(项目号, pid)`。
- `verify-v16.mjs:131` 「原样导回后 pid 集合不变」→ 只要剥离正确仍通过（这是 C6 的回归护栏，别改）。
- `verify-v16.mjs:124` `t0.good.every(r => PID_RE.test(r.pid))` → 依赖剥离正确，同上。

## 6. 不做清单与理由

## 7. 风险与回滚

### 7.1 三条红线（改坏金额链的自检点）

| 红线 | 具体含义 | 自检方式 |
| --- | --- | --- |
| ① 不新增金额真源 | 金额链唯一真源仍是「明细合计 → 费用项总计 → 应付(−优惠) → 已付(Σ有效付款) → 待付」。A1 只改显示函数（`fmt/fmtNum/fmtAbs`），**不得触碰** `detailSum / projectTotal / payableOf / paidOf / dueOf`；A2 **不得写 `book.budget`**；B4 只新增独立 localStorage 键，**不改 `state` 结构** | `git diff src/lib/core.js` 里金额函数零改动；`git diff src/lib/store.js` 里 `state` 顶层键零新增 |
| ② 基线字面不变 | 改完全部 13 项，这 7 个数必须逐分不变：应付 246,055.97 / 已付 188,529.11 / 待付 57,526.86 / 预算 234,688.00 / 结余 −11,367.97 / estTotal 14,875.00 / confirmedPayable 231,180.97。并且「导出 → 原样导回」后再次相等（88 笔 / 384 条零丢失） | `node scripts/verify-all.mjs` + 新增 v17 一致性用例 |
| ③ 单真源不许分叉 | 这 6 个函数各只有一处实现，新代码只许调用：`filters.filterProjects`（列表 + 导出）、`paidOf`（已付）、`catRows`/`catCoverage`（品类与预算）、`overdueGroups`（逾期天数）、`payNo`（付款全号）、`fmt/fmtNum/fmtAbs`（金额文本） | `grep -c` 实现点 = 1；视图内不得出现 `Object.keys(book.budget).length`、`p.object` 拼接编号、`Math.abs(` 格式化 |

### 7.2 风险表

| 风险 | 触发条件 | 影响 | 缓解 |
| --- | --- | --- | --- |
| A1 改 `fmtNum` 语义引发「双信号」 | 某处写成 `'+' + fmtNum(x)` 或 `'超 ' + fmtNum(a − b)`，而值恰好为负 → 显示 `+-800` / `超 -800` | 读数被误读成反方向 | §2.1 已列 8 组必须改 `fmtAbs` 的位置；QA 增加「全站渲染文本不含 `--`、`+-`、`¥-`、`余 -`、`超 -`」的扫描断言 |
| C6 前缀没剥离干净 | `mapRow` 只改了导出没改导入 | 导入时 pid 变空 → 退回「日期+金额」猜行 → 同日多笔串账（**v1.6 已修过的 P0 复发**） | §4 三条硬要求；必须保留 v16 的「原样导回 pid 集合不变」用例作为门禁 |

| C2 精度改精确后溢出 738px | 长数字 + 卡片窄 | 换行/截断 | 主数字容器 `font-variant-numeric: tabular-nums` + `white-space: nowrap`；验收用 `scrollWidth ≤ clientWidth` 断言 |
| A2 有人「顺手补键」 | 「预算表覆盖全部在用品类」被理解成写数据 | 预算键 13→14，`hasBudget` 语义重新混淆 | 口径表 §2.2 明写「不补键」；`verify-t01` 的 `预算键数 13` 断言**禁止修改** |

### 7.3 回滚策略

# 项目费用管理 → 项目管理 · 升级方案

> 版本：方案稿 v1.0 ／ 目标版本：v1.2（P0）→ v1.5（P1）→ v2.0（P2）
> 口径：**工程 / 施工类项目**（装修、门店改造、分包工程）
> 现状基线：插件 v1.1.0，应付 `246,055.97`、已付 `188,529.11`、待付 `57,526.86`、预算 `234,688.00`

---

## 1. 定位

| 维度 | 现在（费用管理） | 目标（项目管理） |
| --- | --- | --- |
| 回答的问题 | 花了多少、还欠多少 | 干到哪一步、该付谁、有没有失控 |
| 核心对象 | 支出项 | 项目（工期 + 合同 + 交付 + 费用） |
| 时间概念 | 只有单据日期 | 开工/竣工、阶段计划与实际、里程碑 |
| 契约概念 | 无 | 合同、付款节点、质保金、变更单 |
| 质量概念 | 无 | 隐蔽验收、材料进场、整改项 |

一句话：**以施工过程为主线，让每一笔钱都能落到「哪个阶段、哪份合同、哪个验收节点」上。**

---

## 2. 三条主线场景

### 场景 A：月度对账（最高频，每次 3 分钟）
打开插件 → 概览看到「本月应付 3.2 万、逾期 1 笔、水电阶段已超支 8%」→ 点进逾期付款 → 记录付款 → 合同节点自动标记已付。

### 场景 B：阶段验收（工程类独有）
水电完工 → 进入「进度」→ 点水电阶段「验收」→ 拍照 2 张、填验收人、结论合格 → 阶段自动置为完成、生成下阶段待办 → 若不合格，生成整改项挂到「交付」。

### 场景 C：增项变更（装修最大痛点）
工长提出加做吊顶 → 「合同」里新增变更单（+4,800，原因：原设计未含）→ 原合同金额不变、变更累计单列 → 预算基准受保护，超支判断改为「预算 vs（合同 + 变更）」而不是直接改预算。

## 3. 信息架构（800px 约束下的导航）

左轨由 6 项扩为 7 项，**不引入二级导航**，每项始终作用于「当前项目」：

```
┌──────┬──────────────────────────────────────────┐
│ 装   │  项目切换 ▾   自宅装修 · 进行中    ●健康  │
│ ──── │──────────────────────────────────────────│
│ 概览 │  KPI 四格 / 阶段时间线 / 今日待办 / 风险   │
│ 进度 │  阶段手风琴 · 里程碑 · 任务 · 验收          │
│ 费用 │  支出流（原列表）+ 预算 + 变更累计          │
│ 合同 │  合同卡片 · 付款节点 · 质保金 · 变更单      │
│ 交付 │  验收清单 · 整改项 · 材料进场 · 附件        │
```

高度核算：品牌 40 + 项目按钮 44 + 7×46 + 主题 34 = **440px**，窗口 618px 内不滚动。
项目列表（跨项目卡片流）从**顶部项目切换器**进入，占满内容区，不占左轨。

## 4. 数据模型

### 4.1 结构

```js
book = {
  // —— 项目档案（新增）——
  id, name, code, color,
  status: 'planning' | 'active' | 'paused' | 'done' | 'archived',
  startDate, endDate,        // 计划开工 / 计划竣工
  actualEnd,                 // 实际竣工
  owner, client, address, tags: [],
  type: 'fitout' | 'mep' | 'civil',   // 装修 / 机电 / 土建，决定阶段模板

  // —— 费用（沿用 v1.1）——
  totalBudget, budget: {}, categories: [], payees: [],

  // —— 进度（新增）——
  stages: [{
    id, name, color,
    planStart, planEnd, actualStart, actualEnd,
    status: 'pending' | 'doing' | 'done' | 'blocked',
    weight,                                  // 金额权重，见 6.2
    milestones: [{ id, name, date, done, doneAt }],
    acceptance: { required: true, at, by, result: 'pass' | 'fail', note, photos: [] },
    items: [{ id, name, owner, planStart, planEnd, done }],  // 任务
  }],

  // —— 合同（新增）——
  contracts: [{
    id, no, party, type: 'labor' | 'material' | 'design' | 'supervise',
    amount, signDate, startDate, endDate,
    retention: { ratio: 0.05, releaseAfterMonths: 12 },
    nodes: [{ id, name, ratio, amount, dueDate, paid, paidAt, paymentId }],
    invoice: { status: 'none' | 'partial' | 'full', amount },
    note, files: [],
  }],
  changes: [{ id, date, scope: 'cost' | 'time', target, from, to, reason, contractId }],

  // —— 交付（新增）——
  deliverables: [{ id, name, stageId, due, status: 'pending' | 'pass' | 'fail', at, by, note, photos: [] }],
  issues: [{ id, title, level: 'low' | 'mid' | 'high', owner, status: 'open' | 'fixed' | 'closed', foundAt, closedAt }],
  materials: [{ id, name, brand, spec, qty, unit, arrivedAt, receiver, result, itemId }],

  // —— 费用明细（原 projects，改名）——
  items: [ /* 原 book.projects 结构不变 */ ],
}
```

### 4.2 关键改名

| 旧 | 新 | 原因 |
| --- | --- | --- |
| `book.projects[]` | `book.items[]` | 加上阶段/合同后，「项目」必须专指 `book`，否则 `projects` 一词语义打架 |
| 界面「项目」 | 「项目」= book | 切换器保持「项目」 |
| 界面「支出项」 | 「费用项」 | 与 `items` 对应，避免与「项目」混读 |

兼容策略：读取时 `items = b.items || b.projects || []`；写入只写 `items`；旧字段在迁移时重命名后不再保留（备份键留档）。

### 4.3 阶段模板（按 `type` 预置）

`fitout`（装修，默认套用现有 14 品类映射）：

| # | 阶段 | 建议里程碑 | 验收 |
| --- | --- | --- | --- |
| 1 | 拆改 | 开工交底 | 否 |
| 2 | 水电 | 水电打压试验 | **是（隐蔽）** |
| 3 | 防水 | 闭水试验 48h | **是（隐蔽）** |
| 4 | 泥瓦 | 墙地砖完成 | 否 |
| 5 | 门窗 | 门窗安装 | 否 |
| 6 | 木作 | 柜体下单 / 柜体安装 | 否 |
| 7 | 涂饰 | 底漆 / 面漆 | 否 |
| 8 | 安装 | 灯具洁具 / 家电进场 | 否 |
| 9 | 验收 | 竣工初验 / 整改完成 / 竣工验收 | **是** |

`mep`（机电）：预埋 → 桥架 → 布线 → 设备安装 → 调试 → 验收。
`civil`（土建）：土方 → 基础 → 主体 → 砌筑 → 抹灰 → 竣工。

阶段与「品类」的关系：**品类是钱的分类，阶段是时间的过程**。默认 1:1 映射（现有 14 品类 → 9~14 阶段），允许用户合并（如「门窗 + 全屋定制」并为「木作」）或拆分。

## 5. 功能规格

### P0（v1.2）

#### F1 项目档案
- 字段：名称、编号、类型、状态、计划起止、实际竣工、负责人、客户、地址、标签
- 交互：设置页「项目档案」抽屉，分三段（基本信息 / 工期 / 干系人）
- 边界：状态改为 `done` 时提示「是否同时归档并冻结编辑」
- 验收：新建项目可只填名称；状态徽标在项目切换器与概览同步

#### F2 项目列表
- 卡片流（单列，宽 700），每卡：名称 + 状态点 + 进度条 + 预算使用率 + 下一节点 + 待付金额
- 排序：状态 → 下一节点日期 → 预算使用率
- 验收：8 个项目在 618px 内可滚动浏览，卡片高度一致（96px）

#### F3 阶段与里程碑
- 阶段手风琴，每段头：序号 + 名称 + 计划区间 + 权重 + 完成度 + 状态
- 里程碑：名称 + 日期 + 勾选完成；勾选记录 `doneAt`
- 阶段状态由「里程碑全完成」自动推为 `done`，可手动改回
- 验收：勾完某阶段全部里程碑，进度% 与概览时间线同步更新

#### F4 隐蔽工程验收
- 触发：阶段 `acceptance.required = true` 时，阶段头显示「待验收」
- 表单：验收日期、验收人、结论（合格 / 不合格及说明）、照片（最多 4 张，压缩至 320px 宽）
- 硬规则：**未验收的阶段不可标记 done**（点击 done 弹出验收表单）；`fail` 时自动创建整改项到「交付」
- 验收：水电阶段未验收时点完成 → 强制弹验收，无法绕过

#### F5 项目健康度
- 四维计算见 6.3，概览头部一个圆点 + 悬停/点击展开原因列表
- 颜色：绿 / 黄 / 红，取四维中最严重者
- 验收：构造超支 12% 的项目 → 判红且原因显示「成本超支 12.0%」

#### F6 语义统一
- 全站「支出」页签改名「费用」，导出表头首列「项目」→「项目 / 费用项」两级
- 迁移：`projects` → `items`，旧键留 `.v1_backup`

## 6. 算法

### 6.1 金额链（扩展后，保持唯一真源）

```
明细金额 → 费用项总计 → 应付(=总计−优惠)
合同金额 + 变更累计 = 契约额（承诺口径）
已付 = Σ付款记录 ／ 待付 = 应付 − 已付
预算基准 = totalBudget + 已批准变更（cost 类）
```

三条口径同时呈现，不再混为一个数：**预算（计划）/ 契约（承诺）/ 实际（发生）**。

### 6.2 阶段权重

```
weight_i = 阶段 i 下所有费用项应付合计 / 项目应付合计
```
无费用项的阶段（如「验收」）按阶段数均分兜底，避免 0 权重导致进度永远到不了 100%。

### 6.3 健康度

| 维度 | 指标 | 黄 | 红 |
| --- | --- | --- | --- |
| 成本 | (应付 − 预算基准) / 预算基准 | > 5% | > 10% |
| 工期 | 今日 − 计划竣工；或阶段计划结束已过 | 1–7 天 | > 7 天 |
| 付款 | 逾期笔数 / 逾期金额 | ≥1 笔且 > ¥5,000 | 逾期 > 15 天或 > ¥30,000 |
| 质量 | 未关闭 high 级整改项 / 验收不合格 | ≥1 项 | ≥3 项或存在未验收却在推进 |

综合：任一红 → 红；无红有黄 → 黄；全绿 → 绿。

### 6.4 进度%

```
stageDone_i = 已完里程碑 / 里程碑数（无里程碑则 done ? 1 : 0）
progress = Σ(weight_i × stageDone_i) × 100%
timeElapsed = (今日 − 开工) / (计划竣工 − 开工)
SPI = progress / timeElapsed   // P2 展示
```

## 7. 数据迁移（v1.1 → v1.2）

新键 `ztools_project_cost_v2`，旧键 `ztools_project_cost_v1` 保留为 `_v1_backup`（只读留档，不自动删）。

```
1. items = book.projects（重命名，结构不变）
2. type = 'fitout'
3. stages = 由 categories 生成：每个品类一个阶段，planStart/planEnd 取该品类下费用项的最早 date / 最晚 effectiveDue
4. 阶段权重按 6.2 计算；无费用项品类权重为 0（保留但不参与进度）
5. status = 有已付且未竣工 → 'active'；无支出 → 'planning'
6. startDate = 全项目最早费用项 date；endDate = 空（由用户补）
7. contracts / changes / deliverables / issues / materials = []
```

迁移后必须满足：**应付/已付/待付/预算/结余 五项与迁移前完全一致**。任何一项漂移即视为迁移失败，回滚到 `_v1_backup`。

## 10. 风险与取舍

### 10.1 明确不做
- 多人协作 / 权限 / 实时同步（需上云端，等于重写）
- 可拖拽甘特图（738px 放不下，用「阶段条 + 里程碑点」替代）
- 工时统计与资源平衡（个人/小团队用不上，录入成本高反噬）
- 发票税务合规、财务凭证对接

### 10.2 两个真实风险
| 风险 | 触发条件 | 对策 |
| --- | --- | --- |
| localStorage 配额（5MB） | 合同扫描 + 验收照片超过约 40 张 | 图片压缩到 320px 宽；超 20 张自动转 IndexedDB；导出 JSON 时图片可选剔除 |
| 概念膨胀 | 7 个分区 + 项目档案字段过多，录入变慢 | 所有新增字段默认折叠；新建项目只强制「名称」；阶段由品类自动生成，零录入 |

### 10.3 取舍
把「任务清单」放在 P1 而非 P0：工程类里，阶段 + 里程碑已能回答「到哪一步」，任务颗粒过细会让 800px 窗口变成待办应用，与「费用台账」的定位冲突。若要任务，建议只做「阶段下 3–8 条关键任务」，不做无限层级 WBS。

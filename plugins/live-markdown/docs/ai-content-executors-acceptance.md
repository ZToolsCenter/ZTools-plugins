# B31 内容执行器：验收与剩余问题

本轮在 `codex/live-markdown-harness-b13` 对应开发 worktree 实施，交付独立测试包。不替换已安装插件，不改用户 Welcome 文稿，不提交或推送。B30/B29 原包及原始证据保留。

## 完成的执行层改动

- 模型填写有界内容 payload，程序生成标题、围栏、JSON、表格、公式定界符和 Mermaid 节点 ID。匹配语言的多余代码围栏可规范化；明确的额外产物后文不适合该模板时，调用前回到自由生成，不静默丢掉后文。
- 润色/校对使用 AST 正文槽，源码负责代码、表格、公式、链接目标、强调边界、换行与指定标记。分批预算先计算，全部完成才形成一个 Diff；不自动重试，不部分写回。
- 来源问答按实际源码范围核验字段、主体和原句；长文逐块扫描。明确字段齐全时可零调用，否则只选择来源 ID，不进行最后一次自由编答案。
- Markdown 基础语法使用固定 CommonMark 0.31.2 资料；文稿标题问题读取真实 AST，不能偷换成语法说明。
- 保留选区/全文/光标、只读、版本、取消、字节和时间预算，以及确认后一次写入、一次撤销。模型协议的中间 JSON 不显示成正文。

设计、接口和边界见 [技术设计](ai-content-executors-design.md)。没有增加依赖或把模型/运行时放入插件包。

## 回测口径与版本

原 79 条用例保留，增加 20 条：共 99 条、其中 34 条代表场景执行两模型 direct/thin/full 三路，共 204 组。其余 65 条是准备好的受控矩阵，条目数量不代表都完成真实模型执行。生产入口单测与浏览器另行覆盖协议和生命周期。

最终模型证据为 `.cache/acceptance/content-executors-b31-20261027/b31-r4-{light,balanced}/`。每次运行均冻结 src/preload 全树、实际用例、评分器、入口脚本、依赖与 Vite 配置，并核验运行前后 SHA；记录模型和运行时 SHA、完整提示词/回执/异常。只用已缓存的 Qwen3 0.6B 与 1.7B Q4_K_M，不下载。`b31-pilot`、`b31-final`、`b31-r2`、`b31-r3` 是保留的中间运行标签，不能与 R4 交付身份混用。

三路保留同样的授权范围和安全写回边界。direct 跳过内容执行器与编译器；thin 为生产默认；full 为当前代码里的显式旧完整流程，包含共用解析修正，并非不可变 B30 二进制。schema 路径温度为 0，raw 路径用后端缺省值，无固定 seed；比较包含协议、提示和采样差异，不能解释成单变量实验。部分程序检查/浏览器同时运行，因此不使用此次延迟作为性能基准。

## 实测中修正的问题

首次模型和浏览器检查暴露的程序缺陷均保留原始日志，未改写为通过：

| 问题 | 修正 |
| --- | --- |
| 代码示例把 Python 占位函数教给其他语言；匹配的外围围栏仍被拒 | 使用中立正文协议、语言单列；匹配外壳规范化，错语言不悄悄改名 |
| “Markdown 二级标题”与 TypeScript 被当成两种代码语言 | 按标题角色排除通用 Markdown 格式词，真实语言冲突仍保留 |
| 保留文首文末标记被当成插入位置 | 保留约束与操作位置分别解释，普通输入润色不再因此被拦 |
| 摘要重点包含预算/状态就被改成字段问答 | 通用摘要保持摘要；明确“只总结某些字段”使用字段投影 |
| 文稿已有项目的字段问答没写“原文”就漏掉来源 | 精确匹配授权源码中已提及的主体后使用来源路径；不相关问题不发送私有文稿 |
| 来源生成表格被不确定操作回答吞掉 | 绑定明确来源转换与授权范围；选区默认选区、明确只回答不建提案 |
| “以 JSON 回答”格式被字段清单覆盖 | 先使用明确答案格式的适配器；无适配器保留普通格式生成 |
| 多词主体/人名截断、英文标签漏掉、相同金额跨主体混淆 | 完整名字边界和有限的中英文显式关系绑定；未知值不借其他主体补齐 |
| 证据 ID 列表固定 256 tokens 会截断 | 按完整回执预估输出并预排必要批次；不截原文，不失败后重试 |
| 背景提到“负责人”“决定”就被当成事实 | 负责人标签要求明确系词/分隔符；决定要求明确声明/行动，排除否定和背景提及 |
| direct 超预算会暗中切 full | direct 保持原策略并在预检失败时停止 |

## 质量复核与未通过项

复核读取原指令、源码、选区、完整输出和错误。代码格式正确不等于代码能运行，原句 ID 存在不等于关系正确；no-op 润色也不能算完成任务。没有增加模型裁判或执行生成代码。

- 原有 7 类复杂任务的 42 条独立复核为 20 通过、16 失败、6 未产出；其中 thin 为 12/14 通过，见 `manual-original-r4.json`。OPEN01 仍出现复述指令、正文省略号等未完成草案的问题。
- 新增 9 个真实场景的 54 条主 Agent 复核见 `manual-added-r4.json`：thin 为 7 通过、10 失败、1 未产出；direct 为 4 通过、14 失败；full 为 1 通过、7 失败、10 未产出。它们是该子集的结果，不是全 204 条统一成功率。

合并这 16 类、96 条人工复核，thin 为 19 通过、12 失败、1 未产出；direct 为 10 通过、22 失败；full 为 3 通过、13 失败、16 未产出。它们不能证明剩余 108 组模型结果的语义正确性，也不能外推到任意文稿。

已验证的收益包括：代码外部标题/围栏由程序生成、明确字段关系和长文首中末决定不需要模型重述、复杂 Markdown 润色不会因复制全文而改坏受保护结构。两个模型仍未取得全面质量验收，以下缺口明确保留：

1. 多标题枚举仍可能被 canonical 参数解析合成一个标题；这属于执行层规格覆盖问题，不能全部归因于模型能力。
2. 代码正文仍可能混入非法语法、生成变量代替预期函数或漏掉行为；围栏/函数名检查不足以证明行为正确。
3. JSON 可语法正确却把 `enabled` 改成 `ok`，也可能产出无法解析的 payload；序列化不能保证字段语义。
4. 来源表格仍可能遗漏货币单位；行和数值对应不等于全部信息完整。
5. 带行内格式、CRLF 等复杂结构的润色，有时完整保留源码却没有改善明显语法错误。

这些结果继续作为可审查候选或明确停止，不自动写入。当前包是执行层改进的测试候选，不声明复杂生成全通过。

评分器另有两项已知预期偏差，原 79 条矩阵未被偷偷修改：TABLE03 的英语来源未要求翻译单元格，冻结 oracle 却要求中文值；B31-CODE-H4 原指令只写“定义 run_check”，冻结 oracle 额外要求函数。人工复核按原指令区分可确认要求和未明确的假设，不把这些差异一概算成模型失败。Mermaid 引号标签的 oracle 误判已修正并测试，原中间报告保留其旧结果。

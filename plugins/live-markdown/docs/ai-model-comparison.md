# 本机模型对比：Qwen3 0.6B 与 1.7B

日期：2026-10-23。结论：**1.7B 部分正文生成更好，但在当前 B6 Harness 下没有提升端到端完成率，不宜直接当作当前问题的整体解法。** 两轮所有失败均保留。

## 实验约束

- 两模型均为已缓存、SHA-256 校验通过的 Qwen3 Q4_K_M；零下载、无单项修复重试。
- 每模型各跑两轮相同 80 场景，共 **320 次任务**；没有挑选最好的一轮。两个模型每轮都按相同顺序执行。
- 共用 B6 产品快照、默认 general 角色、提示词、4096 context、输出额度、分块与 AST/输出契约；量表和全部非配置工具文件逐个哈希相同。
- 本机 Apple M5 / macOS arm64 / 32 GB。两组实际服务记录均为 **Metal**，同一 llama.cpp b11793；不能按模型资源的 CPU 标签误记实际后端。
- 每模型使用独立缓存配置，未写宿主设置或文稿。原验收缓存 active/metadata 哈希保持不变；当前 197 个产品文件仍与 B6 一致，ZIP 也保持不变。

| --- | ---: | ---: |

| 第 2 轮原量表全维度通过 | 52/80 | 50/80 |
| 两轮合计 | 104/160 | 100/160 |
| 每轮字面编辑精确提案 | **40/40、40/40** | **38/40、38/40** |
| 每轮原始意图协议通过 | 72/80、72/80 | 68/80、68/80 |
| 每轮客观内容量表 | 8/18、9/18 | 10/18、10/18 |
| 每轮任务/内容/范围联合通过 | 55/80、56/80 | 54/80、54/80 |
| 每 80 项墙钟耗时，含启动与记录 | 49.82、34.92 秒 | 94.06、68.42 秒 |
| 模型文件大小 | 396,705,472 字节 | 1,107,409,472 字节 |

耗时约翻倍是这次完整任务组合的观测，包含输出长度、任务路由、启动与系统负载，不是纯 token 吞吐比较。只有两个模型和两轮，不能据此推断所有较大模型都更差。上一轮 B6 的 53/80 是另一轮观测，本次比较使用同时重建的 52/80 对照。

原量表没有改动：L25 的合法强调格式替换、T7 B17–B21 的五类受限精确编辑仍会被旧 AST/reject 量表计为失败；独立核验以实际 `error`、`result.proposal.patch` 和源范围为准。两模型四轮的 T7 都实际产出 5/5 精确提案；L25 也有精确提案，不能把旧评分器的 reason 当作产品异常。

## 复杂任务表现

| 场景 | 0.6B | 1.7B |
| --- | --- | --- |
| G03：价格表 | 重复全文，被回声检查拒绝 | 两轮均把表格路由成 diagram，生成 mermaid 围栏包着表格，被格式检查拒绝 |
| G04：Mermaid 三步图 | 两轮均不能形成有效图表 | 第一轮标准三节点代码通过；第二轮关系表面正确，但隐式中文节点被子集量表报错，未实跑解析/渲染 |
| G05：数学解释 | 一轮被拒绝，一轮产生有效公式 | 两轮均产出勾股关系；原始 task=summarize 与冻结 custom 不同，协议分仍失败 |
| G06：Python 函数 | 重复原文，被拒绝 | 两轮核心 add 函数正确，但外层 markdown 与内层 python 三反引号嵌套，前置完整性检查拒绝，未产出提案 |
| G08：富文本全文校对 | 两轮均无完成结果 | 能进入正文处理，但两轮均破坏受保护结构被 AST 拒绝 |
| G09：长文三决定，只回答 | 两轮均保留三组关系，3 次正文调用 | 两轮均误澄清“缺少目标”，没有进入摘要正文调用 |
| G10：相同摘要，文末新增 | 两轮均一次追加，3 次正文调用 | 两轮也均一次追加，3 次正文调用，三组关系保留 |
| G11：长文逐段润色 | 两轮均失败，无部分提案 | 两轮仍失败：截断或 AST 结构变化，无部分提案 |
| G14：技术方案 | 复述插入指令、遗漏约束或添加无依据内容 | 更有条理并保留 8GB、离线、不外发等约束；仍需人工审核，第二轮新增 TinyBERT 建议并非原文事实 |
| G16：续写 | 两轮均被原文回声检查拒绝 | 第一轮杜撰 2026-11-10，被质量量表判失败；第二轮行动清单通过 |

1.7B 的两条字面失败稳定发生在 **L10 光标位置插入**和 **L17 最后一处英文替换**：原文目标明确，模型仍输出 `clarify/missing_target`。这是实际没有完成操作，不是旧评分器误报。

这个对比也暴露了 Harness 与模型的交互限制，不能将所有失败归因于模型大小：

1. 表格被归到 diagram 后，Mermaid system 与格式约束覆盖了用户要求的 Markdown 表格。
2. 代码输出的可识别外包装尚未在前置完整性检查前处理，导致后续窄范围解包逻辑没有机会执行。
3. 长文任务仍受分块的输出预算与结构恢复约束；1.7B 没有在现有配置下完成逐段全文润色。

本轮只对比模型，没有为改善分数改产品、改提示词、改预算或放宽校验。

## 内存口径

两轮完整场景的 RSS 采样均不可用：macOS `ps` 多列输出把程序名截断，身份过滤没有匹配到样本。原记录中的首轮 `0` 及第二轮 `null` 均表示**未取得测量**，不能说占用为零，也不能声称全场景峰值已完成比较。

修正为分列读取、精确核验程序路径后，另做两个模型各一个**相同短请求**的补测：context=4096、max output=128，每 250ms 采样，生成均成功。0.6B 采到 3 个样本、最大 RSS 981,360 KiB（约 0.94 GiB）；1.7B 采到 5 个样本、最大 1,664,112 KiB（约 1.59 GiB）。这是短请求中已采样的进程常驻内存，不代表长文任务峰值、全部 GPU 分配或全系统内存。

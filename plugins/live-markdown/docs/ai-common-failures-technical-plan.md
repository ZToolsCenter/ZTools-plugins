# Live Markdown：两个模型共同失败的技术方案

日期：2026-10-23。状态：待评审方案，尚未实施。依据：[0.6B / 1.7B 同条件对比](./ai-model-comparison.md)、四轮原始记录及独立复核。本方案接续 B6，保留[上一阶段设计](./ai-harness-optimization-plan.md)已经实现的能力，不重复开发。

## 1. 判断与范围

**优先改变模型承担的任务，再判断是否需要换模型。** 两个模型都没有稳定完成表格生成、代码片段生成、富文本校对和长文润色；较大模型有时生成了正确内容，仍被错误路由或验证顺序挡住。只升级模型不能解决这些共同问题。

| 用户任务 | 已确认现象 | 这次解决方式 |
| --- | --- | --- |
| G03 生成价格表 | 0.6B 复述全文；1.7B 被路由到 diagram，Mermaid 约束覆盖了表格要求 | 先锁定用户要求的产物；表格用结构化数据、程序序列化 |
| G06 生成 Python 函数 | 0.6B 复述上下文；1.7B 函数主体正确，但嵌套外围栏在前置检查失败 | 收紧新增内容上下文；统一、提前执行受限解码 |
| G08 富文本校对 | 0.6B 错误澄清；1.7B 破坏保护结构 | 明确字段由程序持有；模型只改可编辑文本槽 |
| G11 长文逐段润色 | 四轮均失败，存在截断、遗漏或结构变化 | 按短文本槽分批调用，程序原位组装，完整成功才生成一个 Diff |
| G14 / G16 技术方案与续写 | 指令回声、约束遗漏、无依据品牌或日期；表现和严重程度不同 | 分开原文事实、约束和新建议，使用来源绑定及有界内容模板 |

两类问题单独记录，不能混为“两个模型都不会”：

- 固定 B6 条件下，1.7B 两轮在 L10 / L17 / G09 都错误澄清，0.6B 没有同样回退；纳入契约回归。这是模型与提示/schema 交互下的观察，不能直接认定为模型固有问题或正文生成能力不足。
- G04 的隐式中文 Mermaid 节点、G05 的内部 task 差异、L25 和 T7 的旧评分分歧，需要独立评分及真实渲染验证。原始分数保留，不改历史量表追溯制造提升。

本轮拟改 Harness、相关评测与既有助手错误状态接线。不扩展本地部署、不自动升级或切换模型、不新增对话轮次或全局“判官”模型、不重写整个编辑器渲染器。

## 2. 必须保持的约束

- 插件 ZIP 与解压资源各不超过 15,000,000 字节，模型、引擎、评测依赖均在包外；保持 Windows / macOS / Linux 的现有宿主适配。
- 无选区默认全文；明确要求选区却没有有效选区时不能退化为全文。
- 自然语言最多一次意图规划；完全由有证据字段构成的操作可零规划。字面内容由程序回源，零正文生成。
- 没有自动重试、失败修复调用或失败后的隐式缩小范围；分片是执行前确定的多次任务，不是重试。
- AST、保护区、范围外源码和写回前的版本校验继续生效。失败不产生可应用的部分提案，不以“安全拒绝”冒充任务完成。
- 生成期间继续编辑；最后一个完整 Diff、一次写回、一次撤销。输入保留，用户可修改指令再发送。
- 不承诺 Harness 能证明任意自然语言语义正确；事实核验和内容质量必须另验收。

## 3. 统一执行契约：程序先确定已经知道的内容

### 3.1 职责分开

现状中 task 同时影响语义提示和产物格式。例如 aiOutputContract.requestedOutputFormat 优先看 semanticAction=diagram，plannedTaskRunner 又根据模型 task 选择 Mermaid system，导致显式表格指令被两处覆盖。

扩展现有指令契约，形成一份只读的执行契约，由入口构建并贯穿规划、提示、正文、解码、验证与提案：

~~~ts
interface ResolvedTaskContract {
  effect: "answer" | "insert" | "replace_exact" | "rewrite";
  task: "custom" | "polish" | "proofread" | "summarize" | "continue" | "tech-spec" | "diagram";
  target: BoundTarget;                 // 源范围、定位依赖和快照证据
  content: "literal" | "generate";
  artifact: "markdown" | "table" | "code" | "math" | "mermaid";
  display: "rendered" | "source";
  facts: "preserve" | "source_bound" | "allow_suggestions";
  requirements: OutputRequirements;   // 列名、语言、必需标题、禁止新增日期等
  evidence: readonly ConstraintEvidence[];
}
~~~

这是解析并绑定后的接口示意；复用现有类型，不另造第二套 target 或 offset 系统。

优先级为：**用户显式要求 → 已选择按钮/Skill 的结构化默认值 → 模型补充未知项 → 普通默认值**。同一指令显式要求互相冲突时澄清，不能用优先级掩盖冲突。artifact=table 不允许 diagram 默认值把它改成 mermaid。

### 3.2 模型只补未知字段

1. 现有引号/否定感知的约束解析只提供有原句证据的字段；源绑定核实光标、匹配序号、章节和选区。未识别保持未知。
2. 字段完整且能唯一绑定时，程序构造计划，不再请模型重复判断。例如明确光标字面插入、最后一处精确替换。
3. 仍有未知项时只发起一次规划，schema 固定已知值，模型只能补未决字段。回答类不要求编辑位置；G09 不应因没有写入位置而报 missing_target。
4. clarify 必须指向仍未解决的字段或已核实的真实冲突。模型把已知光标说成缺失时记 plan_conflict，不覆盖证据、不再次调用。
5. 不能仅删除 clarify 分支来强迫生成；缺选区、同名章节、重复目标无序号仍应在进入正文前具体引导。

按钮、Skills、自定义输入共用同一份最终契约。只整理已经知道的事实，不将解析器扩展成无限同义句模板。

## 4. 富文本新增：降低格式生成负担

### 4.1 表格首期采用结构化产物

G03 不再让模型既推理价格关系、又抄全文、又拼 Markdown。输入只包含用户要求、列定义、授权源关系及少量必要上下文；输出结构限定为列与行。原文已经存在的“水果—价格—单位”关系必须整体回源，不能分别抽数字后重配。

- 模型返回已知来源关系 ID 与列映射，不得引用不存在的 ID。
- 程序从来源回填事实值、按要求排列并转义竖线/单元格换行，生成真正的 Markdown Table。
- 无法可靠结构化的来源可让模型提出候选引用，但必须精确回源并通过列/关系校验；未覆盖的复杂表格能力明确记待验证，不能偷偷转成 Mermaid 或猜数据。
- 最终检查真实 Table 节点、列数、行数、要求列名、值与单位归属，原文前缀不变，一次 EOF 提案。
- 用户明确要求展示表格源码时保留源码展示；表格教学中的字面围栏不作生成物转换。

G04 的真实流程图另做语法与宿主渲染验收。现有 mathAndDiagramRenderer 是手写解析/SVG 实现，并非官方 Mermaid 运行时；不得把正则通过或出现 SVG 当作全部 Mermaid 语法兼容。当前方案先测实际支持的三步图，外部语法参考解析器仅可作为固定版本开发依赖，不进入插件包。若修复需要改渲染器，先抽出同职责解析模块，禁止继续往现有 1681 行文件追加。

### 4.2 将受限解码移到完整性校验之前

现状：aiTaskRunner 多条路径先调用 validateAiOutput，完整性检查已经失败，最终 validateTaskCandidate 中的外围栏处理便无法执行。

改为所有生成入口共用如下顺序：

**传输完整结束 → 有界解码 → 格式及完整性 → 任务/事实契约 → 原位组装 → 完整文档 AST → 提案。**

- 复用传输层已有的 length / 未完整结束拒绝；被截断的结果即使有一段闭合代码也不能当完成。
- 只有“实际代码/表格等生成片段”且整个响应恰是一个可识别 markdown/md 外包装时，才允许剥一层；内部内容须完整、符合指定产物，外面不能有额外说明。
- G06 的三反引号外 markdown + 内 python 不视作合法嵌套 Markdown；可按明确的响应封套语法剥去首尾一层，再解析内部。封套必须首尾完整且唯一，不做全局删围栏。
- 支持不同合法围栏长度的验证；多层封套、不完整内围栏、混合多候选、未知尾部都拒绝。不得补围栏、补公式或截取“看起来正确”的前缀。
- literal、source 展示、Markdown 教学示例、代码中本来存在的反引号内容保持原义。raw 与 decoded 分别留在测试证据中。
- 代码函数的语法/行为是独立验收，产物校验通过不代表函数正确；插件不执行生成代码。

## 5. 富文本及长文编辑：程序持有结构，模型只改短文本

### 5.1 选定方案：有源码归属的文本槽

不再要求弱模型输出整块 Markdown 并准确抄回 LOCAL_AI 保护标记。程序按当前源码 AST 和范围索引，把可编辑自然语言编译成文本槽；语法与保护节点是固定片段。

~~~ts
interface ProseSlot {
  id: string;                         // 当前快照内唯一，绑定 revision
  range: { from: number; to: number }; // 原始 UTF-16 半开范围
  sourceText: string;
  paragraphId: string;
  contextIds: readonly string[];       // 只读，不授予写权限
}
type SlotReceipt =
  | { id: string; status: "replace"; text: string }
  | { id: string; status: "unchanged" };
interface SlotBatchResult {
  protocol: "prose-edit/v1";
  batchId: string;
  edits: readonly SlotReceipt[];
}
~~~

**模型不返回源码 offset，不返回保护节点、不返回整篇文稿；程序核验每个 ID 并映射回唯一源码。** 这是保留结构的校对/润色能力，不是跨结构重排能力。

- 默认编辑普通正文及清单正文；标题、段落边界、列表标记、复选框、代码（含 inline code）、表格、链接及图片、公式、脚注、frontmatter，以及 HTML 标签/属性/注释留给程序。无法可靠区分正文与 HTML 结构时整块保护。现有明确精确修改继续走既有 MutationPolicy，不经过此能力。
- 强调等 inline 语法分隔符固定；其中可识别的文本可成为独立槽。复杂或边界不可靠的结构整段保护，不凭正则把 Markdown 当纯文本。
- 段间空行、原 CRLF/LF、缩进与槽间分隔符来自原文；槽在行分隔处切开，replace 结果不允许新增 CR/LF。重复段落用 ID 区分，禁止通过全文 indexOf 反推归属。
- 先按自然段、句子边界缩小文本槽，再按实际预算组批；不切开代理对、CRLF、inline code 或保护节点。极长且无法安全切分的内容在调用前说明限制。
- 每批提供有界的段落/相邻只读语境，模型只给当前 owned slots 回执。不得在跨强调、跨句槽或跨段范围任意移动信息；需要此类结构性重写的请求不降级伪装成普通润色。
- G08 必须真正纠错；G11 必须逐段有意义地完成处理，不能返回全 unchanged、遗漏后段或缩写成摘要来通过。质量由冻结正向用例和人工标准独立核验，回执本身只证明处理协议完整。

### 5.2 预先分批，完整覆盖后一次组装

1. 准备完整计划：槽清单、固定片段、owned ranges、只读上下文、每批输出最坏预算和必需事实。固定片段 + 可编辑范围必须精确覆盖授权源码且不重叠。
2. 调用前计算完整 system、指令、上下文与响应 JSON 开销，并保留输出余量。实际放入 prompt 的 schema 才计入 token；独立传输的 schema 单独限字节/深度，不重复计费。text 替换可能变长，不能仅按输入 token 把批次塞满。
3. 使用原 AiTaskExecution：默认一个活动推理请求，串行处理；一次规划与全部分批共用 64 次 / 300 秒限额。计划超限即前置停止，不在执行中临时增加批次或重置额度。
4. 严格解析有界 JSON，限制字节、深度、项数并核对 protocol/batchId；每批必须对 owned slots 恰好回执一次。未知、重复、缺失、越权 ID，异常扩张、非法语法注入、事实改动、截断均停止。unchanged 使用原槽文本；replace 不允许隐含删除整槽。校对/保留结构润色每槽初拟上限为原 UTF-8 字节数的 2 倍加 64 字节，任务级上限还要同时成立；这是待冻结验证的容量预算，不能用截断凑合规。
5. 槽替换不解释为新增 Markdown 语法。用 AST 上下文检查特殊字符是否改变父结构；无法保持结构就拒绝，不能擅自 escape 或改变用户文稿字面内容。
6. 程序按原始范围从后向前应用到临时候选，范围外字节一致；固定节点和关系保持。校验完整文档 AST，再产出一个 Diff。
7. 任一批失败、取消、换文件/模型或写回前 revision 变化，均不能应用先前已完成的部分。保留指令和阶段信息，不自动再发同一批。

保守编辑与摘要账本是两个清楚的执行分支。**现有 G09 / G10 的关系账本、3 次正文调用成功路径保留，不改回自由 map/reduce。** 只把执行契约和公共预算接到同一入口，不为复用而把“改写正文”和“抽取事实”混成一个返回类型。

G11 旧量表的 8–16 调用不是新实现的正确性定义；当前输入实际计划可能细分为 17 块。新配方在实验前冻结实际槽/批清单及调用数，质量要求和所有段落覆盖保持不变，旧量表继续留档。

## 6. 事实与指令：生成内容也需要约束

### 6.1 明确三种能力

| 契约 | 用途 | 程序可做的约束 |
| --- | --- | --- |
| preserve | 校对、保留结构润色 | 固定节点原样；数字、日期、金额、单位、实体归属及显式约束保持 |
| source_bound | 严格基于原文的摘要、表格、技术方案 | 核心事实来自已验证来源；不把新品牌、日期、性能承诺写成原文事实 |
| allow_suggestions | 用户要求下一步、风险建议或创作 | 来源事实仍锁定；新增建议允许，但与既成事实分开，遵守“不得编造日期”等显式禁令 |

facts 策略由指令证据和任务共同确定。G14 的“严格基于原文”采用 source_bound；G16 的行动建议允许具体检查建议，但不允许编造发布时间或金额。不能靠一个“creative=true”绕过用户的事实限制。

### 6.2 先缩小自由生成面

- 复用 summaryFactLedger 中的来源引用和关系组，为生成分支提供任务所需的少量已验证事实与必需约束；选区任务只取授权选区。
- G14 的目标/方案/风险先形成固定小节，模型只填短正文；source_bound 事实条目引用已知事实 ID，由程序回填或核对。8GB、离线、不外发等显式约束有覆盖要求，不能只保留项目名就算完成。
- 原文事实与“可建议事项”在响应 schema 中分开。source_bound 不接受未经来源支持的新产品品牌/配置结论；无法证明任意叙述受原文支持时，使用较保守的来源条目组织，或明确该能力尚未完成，而非给出“已验证真实”标记。
- G16 的建议使用授权目标、已有发布前提构造短行动项。日期、金额、负责人不得变成新值；没有必要引用的数字不要求模型复写。
- 控制信息如“全文末尾插入”只进入执行层，不作为正文主题。字面内容从原句回源；生成内容只收到内容要求和只读事实。
- 回声检查按产物执行：追加/续写不能抄全文；摘要允许选定原句，代码中的指定函数名、表格中的指定列名不算指令回声。不能为了去回声删除必要事实。

词法白名单只能发现一部分数字/日期/已识别实体错误，不能证明关系或自由文本全部正确。来源关系变更、否定变肯定、主体互换需要标注测试和人工复核；不追加一个自评模型来声称证明了真实性。

## 7. 模块边界与实施归属

以下是设计归属，允许实施时根据已有模块微调命名；不得另建一套平行入口或把整套逻辑塞进现有 runner。

| 责任 | 现有接入位置 | 拟新增/提取的独立职责 |
| --- | --- | --- |
| 执行契约、已知字段解析 | instructionConstraints、intentOutputSchema、intentPlanValidation、plannedTaskRunner | 产物/事实要求的契约解析与解析后约束；位置仍用 intentBinder |
| 响应封套与候选检查 | aiTaskRunner、validateAiOutput、aiOutputContract、finalizeAiTaskOutput | aiResponseDecoder：单层有界解码；公共候选校验只执行一次 |
| 表格数据到产物 | plannedTaskRunner 的表格正文分支 | aiTableArtifact：来源映射、表格序列化和实际节点验证 |
| 文本槽与安全分批 | aiTaskRunner 的 conservative 分支、aiChunkPlanner | proseEditPlan：源归属与预算；proseEditExecution：回执验证、原位组装 |
| 来源绑定的生成 | 已有 summaryFactLedger、输出契约 | groundedGeneration：有限事实/建议结构、约束覆盖；不修改摘要归并语义 |
| 会话与写回 | useAiTaskSession、现有 proposal 应用逻辑 | 主 Agent 串行接入新结果并审查取消、版本、Diff 与 Undo |

新增职责必须可独立测试，文件不超过 500 行。aiOutputContract 当前 421 行、aiChunkPlanner 448 行、instructionConstraints 428 行，不在其尾部堆新流程。模型无关的核心保持 TypeScript；平台适配只处理原有进程/文件路径与测量差异。

## 8. 性能与操作边界

- 默认保持一个模型、一个活动调用；不并行占用本地小内存机器，不增加 embedding、向量库或额外服务。
- 源码按 revision 解析并建立槽/事实索引，范围切片复用；缓存限条数和字节、版本变化失效，不持久化完整文稿。
- 复用现有 1 MiB 输入、50 块、64 调用、300 秒总时限以及 provider 的 context/output 上限；新批次更短但不得突破既有上限。超限不是任务完成。
- 新分槽流程同时设置聚合界：初拟每任务累计 raw 响应（含规划/JSON）≤2 MiB，最终文档候选≤1 MiB；前置冻结每批申请的最大输出 token 总和，不能超过共享剩余调用数与 provider 单次输出上限的乘积，执行中逐次扣减。没有真实 usage 时报告申请上限与 token 估算，不冒充实测 token。每批校验后释放 raw，只保留受限回执和源引用；组装前核算候选大小，不能累积 64 份 1 MiB 响应后才发现超限。
- 典型约 12k 字符非模型处理 P95≤50ms 作为待验收预算；1 MiB 仍需测主线程最长阻塞与编辑响应。既有边界观测约 382ms，不能说性能已达标。
- 分槽的主要目标是完成质量，不能保证比当前提前失败的两次调用更快。只在同一正向质量门槛下比较成功任务耗时、token 与调用数，同时报告总完成率；不靠缩短输出或安全拒绝制造性能提升。
- 若实际组槽/AST 处理超过编辑响应预算，优先把独立索引/验证作业移到 Worker，并携带 revision/cancel 标识；不将整个交互或宿主 API 移入 Worker。只凭架构偏好不提前加重依赖。
- 生产日志只记录阶段、稳定错误码、耗时、调用数、大小、版本与哈希；开发评测在隔离缓存保存 raw/decoded/slots/facts 证据，不默认采集用户正文。
- 进度为“理解指令 → 处理第 n / N 组 → 检查修改”；失败指出意图、格式、内容约束或具体分组。没有重试按钮，不再出现“正在第1次重试”的残留状态。

## 9. 先冻结评测，再动产品

保留 B6 与四轮 320 项原始结果，新建评测版本；不得覆盖案例或改旧分数。先用新规则重放旧 raw / proposal 和真实渲染，无法离线重放的阶段明确标 N/A，再冻结新输入、产物、配置、模型、预算和留出集。

分开报告：意图协议、精确操作、正向任务完成、内容质量、AST/范围安全、宿主渲染、调用/耗时/内存。不能把内部 task 枚举差异等同失败，也不能用安全拒绝充当正向完成。

上述是发布目标，**不是已测通过率**。每个能力有自己的支持状态；任何目标未达标就保持未验收，不调低质量要求或自动换模型。

正式对比沿用已缓存的两个模型、同一真实角色/Skill 配置和固定运行时；每模型至少两轮，交错运行顺序并逐轮保留失败，不取最好轮。输入/目标/约束相同，确定性的契约与预算算法一致；因模型输出产生的执行分支差异仍应记录，不能隐去。留出集在产品修改前冻结，加入新名称/数字/日期和结构变体，禁止将测试词写入产品规则。

完整运行 RSS 必须修复为平台适配、精确进程身份验证、独立读取 RSS；取不到标 N/A。报告覆盖率、采样间隔与已采样最大值，不把短请求样本当整套峰值或 GPU 总内存。耗时按规划、正文、验证及墙钟分开，零正文调用不掩盖意图调用。

实施后运行现有 typecheck、相关单元/集成/端到端检查；最终执行完整 build 和包体核验。macOS ZTools 开发目录实测与 Windows/Linux 的真实推理/编辑/取消/路径恢复分别记录；没有对应环境不得宣称三平台已验收。

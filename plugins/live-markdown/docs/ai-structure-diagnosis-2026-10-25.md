# 全文 AI 操作的结构报错排查与修复方案

日期：2026-10-25，America/Los_Angeles。当前产品源码仍与 B12 的 213 项清单一致。本轮只排查、测试和提出方案，没有修改产品代码、放宽门禁或重打包。

## 结论

当前 Harness 确实存在分片和门禁分类问题；小模型输出也不稳定。不能把失败统一归为“文稿太长”或“模型太小”，也不应关闭 AST 校验来让坏输出通过。

截图文案属于占位保护标记的数量／顺序校验，不是输入长度或 token 预算门禁的专用文案。本轮当前构建的三种快捷操作没有复现截图的同一条文案，却复现了全文润色／校对被其他门禁拒绝的情况。截图为 3,403 字符，本轮使用内置 Welcome 的 3,400 字符，不能声称逐字重现原现场。

## 已证实的三个 Harness 问题

### 1. 保护数字时切断了完整表达式

`proseEditPlan` 将示例中的上下标表达式切成可编辑槽和受保护数字：

```text
槽：、化学分子式 H~
只读后文：2~O 下标与数学幂次 x^2^ 上标。
```

1.7B 在润色和校对中，都将整个 `H~2~O ... x^2^` 后文复制进前一个槽。程序随后仍保留原本受保护的数字及后文，候选就会重复数字／内容；数字门禁对此拒绝有依据。问题在于模型拿到的编辑单位不完整，而不是应当允许它改动受保护数字。

独立无模型探针也复现了同一切分：`化学分子式 H~`、`~O 下标与数学幂次 x^`、`^ 上标。`。相关实现：[proseEditPlan.ts](../src/core/ai/proseEditPlan.ts)，`literalRanges` 及文本槽范围计算。

### 2. 状态词检测会把介词误当结论

`proseEditFactGuard` 对 `完成|通过|失败|…` 做不区分上下文的词法匹配。独立调用当前公共校验函数：

| 输入 → 合规预期 | 实际 |
| --- | --- |
| `可通过快捷键打开面板。` → `可使用快捷键打开面板。` | 被当作“原有结论或状态词变化”拒绝，属于误拦截 |
| `验收已通过。` → `验收未通过。` | 被拒绝，保护应保留 |

本次 0.6B 的实际变化为将 `，可通过` 改成 `、`；它本身未被认定为合格校对，不能因为状态词分类有缺陷就放行这条删除。可靠误判证据是上面单独构造的同义介词改写。

相关实现：[proseEditFactGuard.ts](../src/core/ai/proseEditFactGuard.ts)。[可重跑的红灯探针](../.cache/acceptance/structure-diagnosis-20261025/guard-probes-1792986971508/run.mjs)及[探针输出](../.cache/acceptance/structure-diagnosis-20261025/guard-probes-1792986971508/report-1792987094980.json)未调用模型、未改产品。

### 3. 摘要候选库会制造 Markdown 碎片

`summaryFactLedger` 在任意 `!` 处分句，没有先排除行内代码和 GFM 提示框标记。它把完整的 `[!TIP]`、代码里的 `[!NOTE]` 等切开，再为碎片分配合法事实 ID。

真实来源 `sf:1559:1568:other` 的 quote 为：

```text
TIP]`、`[!
```

两种模型都实际选中了它，程序将它直接渲染进最终摘要。完整来源切片校验能证明“摘自原文”，却没有证明它是完整句子或合法 Markdown 单元。

0.6B 还选择了 `[!TIP]` 提示框被切开的两半，以及大量原文事实。最终 4,792 字符来自程序逐条拼接源文和章节包装；不能把它理解为模型一次输出 4,792 字，更不能据此判断 token 超限。

相关实现：[summaryFactLedger.ts](../src/core/ai/summaryFactLedger.ts) 的 `sentenceEnd`、`splitSentences`、`paragraphRanges`、事实验证及渲染；[aiSummaryPipeline.ts](../src/core/ai/aiSummaryPipeline.ts) 对合法 ID 的选择与合并。

## 修复方案及验收

1. **先修语法原子边界。** 将 `H~2~O`、`x^2^`、数字与单位、完整行内代码、公式、链接和提示框标记作为完整单元；不向模型提交半个表达式。保护内容由程序保留，正文槽与只读上下文边界明确，减少模型复制相邻文本的机会。
2. **修正事实门禁的分类。** 保留真正状态翻转、数值、身份、URL、公式和结构保护；结合源句及相邻语境识别“审批通过”等事实锚点，允许“通过快捷键／使用快捷键”这类不改变事实的表达变化。校对和润色的允许改动范围分别验收，不能简单删掉整个状态门。
3. **修摘要抽取与全局输出约束。** 分句先尊重代码及提示框边界，禁止半个语法 token 成为事实候选；排除单独 `[TOC]` 等结构标记。默认摘要应有全局要点数和长度目标，去重并择要，不把整份事实台账加章节包装直接当摘要。
4. **补充失败诊断。** 区分预算不足、输出截断、槽回执不完整、只读上下文复制、真正结构损坏、事实门禁拒绝；给出段号与具体差异。记录构建身份、真实 action／Skill、finish reason 和可用用量字段，避免只显示一个笼统橘色提示。

继续保留最终 AST、源快照校验、完整 Diff、确认写回和一次撤销。按此前要求不增加自动修复重试。

修复后的验收必须包含：相同六个真实按钮任务、带明确错字的富文本正向校对、上下标／提示框原子完整性、介词同义改写可通过而真正状态翻转仍拒绝、摘要不长于原文且无碎片。保留各轮原始失败记录；工程检查和内容完成度分别报告。不能用本轮“安全拒绝”或“有提案”作为功能已完成的证据。
